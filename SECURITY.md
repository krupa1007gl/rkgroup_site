# Security notes

## Секреты и данные, скомпрометированные в истории git

До рефакторинга (ветка `backend-refactor`) в репозиторий были закоммичены:

- `rkgroup_site/rkgroup/settings.py` — хардкоженный `SECRET_KEY` (заменён в этой
  ветке; **старый ключ считается скомпрометированным**, использовать его
  где-либо больше нельзя).
- `rkgroup_site/db.sqlite3`, `rkgroup_site/visits.xlsx`, `rkgroup_site/leads_csv/*.csv`,
  `data/leads/**`, `data/visits/**`, `data/backups/**` — файлы с потенциально
  реальными данными обращений (имена, телефоны, email посетителей сайта).

Этот коммит убирает эти файлы из **текущего состояния** репозитория
(`git rm --cached`), но сами блобы остаются в истории git и доступны любому,
у кого есть клон репозитория или доступ к GitHub. Простого удаления файла
из HEAD **недостаточно** для реальной защиты данных.

### Что нужно сделать владельцу репозитория (не выполняется автоматически)

1. **Считать все данные из перечисленных файлов утёкшими.** Если в
   `leads.xlsx`/`db.sqlite3`/CSV были реальные телефоны/email клиентов —
   это утечка персональных данных, которую стоит зафиксировать как инцидент.
2. **Переписать историю git**, чтобы физически удалить эти блобы:
   - [`git filter-repo`](https://github.com/newren/git-filter-repo) (рекомендуется):
     ```bash
     git filter-repo --invert-paths \
       --path rkgroup_site/db.sqlite3 \
       --path rkgroup_site/visits.xlsx \
       --path rkgroup_site/leads_csv \
       --path data
     ```
   - либо [BFG Repo-Cleaner](https://rtyley.github.io/bfg-repo-cleaner/):
     ```bash
     bfg --delete-files db.sqlite3
     bfg --delete-folders "data,leads_csv"
     ```
3. После переписывания истории — **force-push** переписанной ветки и
   уведомление всех, у кого есть локальные клоны, что им нужно перекло­нировать
   репозиторий (старые клоны и форки всё ещё будут содержать утёкшие данные).
   **Это разрушительная операция — выполнять осознанно, отдельно от этого PR,
   и только после согласования с владельцем репозитория.**
4. Проверить, не публиковался ли репозиторий как публичный где-то ещё
   (форки, зеркала, CI-кэши) — там данные тоже нужно чистить отдельно.

### SECRET_KEY

Старый `SECRET_KEY` заменён новым, который живёт только в `.env` (не
коммитится). Если приложение когда-либо работало в проде со старым ключом —
имеет смысл также инвалидировать все текущие сессии Django
(`django.contrib.sessions` таблица) после деплоя новой версии, так как
старые signed-cookie сессии были подписаны скомпрометированным ключом.
